THE THREE MODELS — all on one rented RTX A6000 (48 GB): 14,477 MiB in use at a 32k context, flat through a full show (measured 2026-10-01; at 16k: 14,195). Fits the 3090’s 24 GB; a 16 GB card is a wish, not a target.

THE WORDS — NVIDIA Nemotron Nano 9B v2 (August 2025). 9 billion parameters; a hybrid architecture: mostly Mamba-2 (state-space) layers and only 4 attention layers, so its memory per token of context is small (about 16 KB, against 32-64 KB for the transformer models we compared): the 32k context costs about 0.5 GB of KV cache (calculated). Context supported: 128K; we run 32,768 tokens, one slot. Quantized to Q4_K_M (GGUF by bartowski): the file is 6,223 MiB; llama-server holds 7,046 MiB at 32k. Served by llama.cpp (server build b11096, CUDA), every layer on the GPU. A reasoning model: the show turns its thinking off (/no_think), and a GBNF grammar forces the screenplay format. Why it won our survey (2026-09-14): no refusals on dark fiction out of the box, strong role-play for its size, IFEval 90.3.

THE VOICES — Qwen3-TTS (Alibaba’s Qwen team), checkpoint Qwen/Qwen3-TTS-12Hz-1.7B-Base: 1.7 billion parameters, 24 kHz audio, ten languages, no watermark. Voice cloning from a reference clip (at least 2 s): each character has one real human recording per mood, from the EARS dataset (Meta and the University of Hamburg, CC BY-NC 4.0). Run by faster-qwen3-tts (a speed fork using CUDA graphs) behind tts-serve 1.2. 6,530 MiB on the GPU.

THE EARS — OpenAI’s Whisper, model “small” (about 244 million parameters; open source), served by whisper-fastapi in a container pinned by digest. 888 MiB on the GPU. The app sends the cast’s names as Whisper’s prompt, so it spells them right; a transcript filter decides whether the listener said words or nothing. The only piece from OpenAI is the open one.

Steve Corbett’s projects: TalkWithMe became our fork, TalkWithZombies; tts-serve is the voice server, untouched.

Tech overview

About 5 minutes.

The machines

Two machines and a tunnel. The laptop runs the browser and TalkWithZombies; the AI runs on a GPU box, a VM on Hyperstack for the demo, or a home lab PC with a 3090. One command installs the client, one deploys the AI; during the show, an SSH tunnel brings the box’s three services to the laptop’s localhost. Where things run, not how the playbook works (that is the deep dive).

THE LAPTOP — make client-mac (a standalone Ansible playbook that never reads the deployment’s inventories): clones TalkWithZombies at a pinned tag (today tz-0.6) into ~/TalkWithZombies-client, makes a virtual environment, installs the requirements with pip, and seeds settings.yaml pointing at the tunnel’s ports. The app is FastAPI (Python 3.10+), served on 127.0.0.1:8000. A page on http://localhost counts as a secure context, so the microphone works with no certificate, domain or TLS. The demo laptop is an M1 with 16 GB: it runs no model. macOS proven; Linux likely, never tried; Windows unknown.

THE DEPLOY — make ans-deploy ENV=cloud: Ansible over SSH from the laptop. It starts from “an SSH-able Ubuntu box exists”, so nothing is provider-specific. Checks first: the right environment, no placeholder left, Ubuntu, Docker, the NVIDIA container toolkit, a driver able to run CUDA 12 — it asserts them, never installs them. Then: llama.cpp in a pinned container (build b11096), Whisper in a container pinned by digest, tts-serve 1.2 as a system service. From zero in 7 minutes (ok=33 changed=16); the models are about 11 GB to download the first time; a second run reports changed=0 in 30 seconds. The services start again at every boot, and are bound to the box’s loopback.

THE TUNNEL — make ssh-tunnel ENV=cloud: one ssh -N with three forwards (llama :8080, tts :8001, whisper :8002), keepalives every 30 s (it gives up after 3 missed), and it fails at once if a port cannot be forwarded. Security: none of the services asks for credentials — the SSH key is the whole authentication; the provider’s firewall opens only port 22; the deployment offers only its own key, accepts a new box’s host key on first contact and refuses a changed one, in its own known_hosts (~/.config/zombie-radio/). make check asks the three services for their health through the tunnel.

THE NETWORK — the laptop sends each line to the voice with the character’s reference clip: 590-750 KB per request (WAV, base64). On a home connection that is lost in about 0.5 s per request; on a slow venue Wi-Fi it could add a second or more (a compressed-clips switch is a follow-up). Round trip from the laptop to Hyperstack’s CANADA-1: about 58 ms.

THE BOX — Hyperstack’s RTX A6000, 48 GB, about $0.50-0.59 an hour (provider survey, 2026-09-13); Ubuntu images with Docker and the NVIDIA toolkit preinstalled. A new VM needs a public IP attached and SSH enabled in the console. A stopped VM keeps billing; only hibernation stops it — and restoring needs the same GPU in stock, and no process survives (a full service start). The whole stack uses 14,477 MiB of the 48 GB.

THE HOME PC — the same playbook (make ans-deploy ENV=local) to a Linux desktop with an RTX 3090 (24 GB): Ubuntu 22.04.5, driver R580, Docker with the NVIDIA runtime — the checks passed.

The components

The same picture, opened up: the laptop’s two parts and the box, the colours the same. A few words on each component. Three presses of the arrow key: the browser, then the app, then the GPU box.

GBNF = GGML BNF: Backus-Naur Form, the classic notation for grammars, in the dialect of GGML (the tensor library under llama.cpp). llama.cpp uses it to constrain sampling: at each step, tokens the grammar does not allow are masked out.

THE BROWSER — the page is a small state machine (idle, generating, playing, listening) and it is the show’s clock: it asks for the next round when the voice has drained. Lines arrive as server-sent events while the model writes them. The voice player cuts each line into chunks of whole sentences (about 100 characters) and plays them in order, each in the speaker’s voice and the line’s mood. The microphone is held only while the radio listens: a 10 s window, a press capped at 30 s. The static bed and the gauge (the magic eye, the oscilloscope) tap the page’s audio through Web Audio. Keys: Space held to talk, M mutes the static, F flips its AM filter. Looks: the 1950 Philips radio and a ham transmitter, both restyling the same page; /show opens a chooser with live miniatures.

THE APP — TalkWithZombies, our fork of TalkWithMe; the show engine is about 1,900 lines of Python (app/show/), with 1,284 Python tests plus five Node test suites for the page. Three endpoints: /api/show/start (opens a run, picks the seed), /api/show/round (plans and streams one round), /api/show/listen (transcribes a press). - The model has no memory between requests: every request carries the whole show so far — the cast sheet as the system message (identical each time, so the server’s cache serves it), then each round’s instruction and the lines the model wrote. - The director plans each round in plain Python. Two modes: Broadcast (the receiver is dead; the cast talk, events happen, every 60-180 s of audio the receiver comes back and Samantha calls out) and Contact (the listener speaks; up to 5 ± 1 answers, then the receiver breaks down; two silences and it is switched off). - Every round has an emotional overtone (positive, neutral, negative) that picks its moods, its tone word and its event. The story lab-outbreak has 289 events. - Fixed lines: what the listener must not miss (an event, the call, the breakdown) is said word for word by a cast member, not written by the model. - The grammar allows only the round’s speakers, its line count, its moods, and plain text — said in the instruction in the same words, so the model is guided, not fought: a grammar that agrees with its prompt costs 0.3-0.5 % per token. - The trim keeps the script inside the 32k context (deep dive). Whisper’s likely inventions — empty text, low confidence, known hallucinations — count as silence. - Every run is recorded in runs//script.json; with debug on, every prompt, request, reply and voice chunk is kept. The seed drives every choice and every model request: the same seed replays the same show on the same box and build.

THE BOX — llama.cpp, tts-serve and Whisper; see “Local AI only” and “The machines”.

A git hook blocks any commit of a wired file (the never-commit hook): addresses never reach the public repo. make ans-unset ENV=cloud restores the placeholder when the box is gone. - ans-deploy ENV=cloud runs site.yml against the box. Idempotent: from zero or from any half-done state, it converges; a healthy box reports changed=0 (in about 30 seconds). The first deploy downloads about 11 GB of models: about 7 minutes once apt has finished on a fresh VM, budget 15. Each run is logged on the laptop in ~/.config/zombie-radio/logs/; ANS_VERBOSE=1 adds detail; ANS_ARGS passes extra options (ANS_ARGS=-K asks a sudo password, for a home PC). make ans-check-syntax ENV=cloud parses the playbook without touching a box. - client-mac checks it is on a Mac with git, python3, say and afconvert (it installs none), clones the fork at its pinned tag, makes the virtual environment, seeds settings.yaml with the tunnel’s ports, and creates four placeholder personas with voices made by macOS’s say. A locally modified clone fails loudly instead of being overwritten. The real cast — EARS recordings, one per mood — is two more lines: fetch_ears.py downloads the four speakers’ clips (p007 Daniel, p017 Ralph, p026 Moira, p063 Samantha; about 23 emotions each) into zombie-radio-datasets/ears/, outside git, because EARS is CC BY-NC; cast_voices.py then copies them into ~/TalkWithZombies-client/Personas/ as ref.wav and ref-.wav, evened out in loudness. One tunnel at a time: the cloud’s and the home PC’s use the same local ports. Destroying the box and deploying a new one is also fine: one command, about 15 minutes. - Status, logs, the GPU, the health checks: docs/runbooks/box-inspection.md.

Live demo

Switch to the app and start a show; pause it to comment. Voice instabilities and the known defects (a line said under the wrong name) explained openly. Fallback: Task 7’s video.

BEFORE (backstage) — tunnel open and make check shows three ok; app on 127.0.0.1:8000; open http://localhost:8000/show, pick a look; browser full screen, zoom 100 %, sound output on the room’s speakers. The installed client runs the demo’s defaults: debug off, a random seed per run, static bed on, filter off.

STARTING — press Start: the browser asks for the microphone once, then. The first round is the slowest (about 6.8 s, the voice cold); later gaps 3.7-4.9 s, filled by the static. If Start shows an error, read it: a context too small, or a persona without a voice.

WHAT THE AUDIENCE HEARS, IN ORDER — Samantha’s sign-on (who they are, where, the receiver is dead), then the cast talking among themselves, an event read out every 2 ± 1 rounds. 60-180 s of audio after the start, THE CALL: someone says the receiver works again and Samantha calls out — the RECEIVER sign lights and the radio listens.

TALKING BACK — after the call (and after each answer), “Listening… 10 s” and the Hold to talk button lights. Hold the button or SPACE while speaking, let go when done (a press is capped at 30 s). Say a character’s name to pick who answers (“Samantha, can you hear me?”); they ask who you are first, then where you are, then what they need (supplies, a way out, help finding the lab). Your words show as a caption; doubtful words are marked. 5 ± 1 answers, then the receiver breaks down. Silence: one re-call; two silences in a row and the receiver is switched off.

KEYS — SPACE hold to talk · M mute the static · F flip its AM filter (the old-radio band). Stop and Resume on the bottom bar.

PAUSING TO COMMENT — press Stop: it cuts the voice and abandons the round in flight. Resume continues the same run (after a listening round, the window opens first). A page reload starts a new run.

IF SOMETHING GOES WRONG — “the round request failed”: the tunnel (curl localhost:8080/health), then Resume. Lines but no sound: the browser’s sound, then the voice (localhost:8001/capabilities). No static: M was pressed. The talk button never lights: the microphone was refused — allow it and reload. If the network or the box is gone: the canned video.

WHAT MAY HAPPEN, SAY IT OPENLY — a voice wobbles or garbles a word now and then (cloned voices, one recording per mood, the mood clips set the level: some moods are quieter); a cast member may say another’s line (Daniel introducing himself as Samantha, seen once); the cast improvise places and details — that’s the feature, not a bug.

Tech deep dive

About 8 minutes.

Behind the curtain: one round

The browser is the clock: it asks for each round when the last one has played. The director, plain Python, plans the round; llama.cpp writes it under a grammar; the parser cuts the stream into lines as they arrive, and each line goes to the voice before the next is written. When the radio listens, the listener’s words come back through Whisper.

WHY THE BROWSER IS THE CLOCK — decided 2026-09-21 among three placements: (1) the browser as metronome, the server as director — adopted; (2) a server-side loop pushing to the page — the upgrade for an unattended booth, nothing in (1) blocks it; (3) an external process polling — rejected. The reason: each decision sits where its information is — the story on the server, time in the browser, which alone knows when the audio has finished. It reuses the page’s existing server-sent events, and cost a day less. Its one weakness: the browser tab must stay in the foreground.

THE PAGE’S STATES — idle → generating → playing → listening → idle. Generating: lines stream in and the first ones already play while the model writes the rest. Listening is entered only when the audio queues are empty: half-duplex by construction, so the microphone never hears the cast and Whisper gets only the listener.

ONE ROUND, IN NUMBERS (measured on the A6000) - The gap between rounds: 3.7-4.9 s once warm (6.8 s for a run’s first round, the voice cold; 8.4 s after a trim): the model’s first line takes 0.76-0.94 s through the app and the tunnel, then the voice synthesizes the first chunk. The static bed rises in that gap, so it never sounds dead. - The request: one POST to llama.cpp’s /v1/chat/completions, streamed, carrying the whole show so far, the GBNF grammar in a top-level “grammar” field, max_tokens 512, and a seed (the run’s seed plus the round’s number). - The prompt: the cast sheet as the system message — identical every time, so the server reuses its cache and only the new part is read fresh; the system message starts with /no_think, which Nemotron’s chat template turns into an empty, closed — so the reply, and the grammar, start in the script, not in hidden reasoning. - The grammar is applied at sampling: before each token, every token that would break the format is removed. When the model already wants a legal token, nothing changes — same seed, same text: measured cost 0.3-0.5 % per token; about 10 % when it has to overrule the model. - The voice: each line is cut into chunks of whole sentences (up to about 100 characters) and each chunk is one request to tts-serve, with the speaker’s reference clip for the line’s mood. - Server timings measure the work, not the wait: the app keeps the server’s own token counts (prompt read fresh, reused from cache, written) — they size the script for the trim.

NOT BUILT (a follow-up): prefetching round N+1 while round N plays, which would hide the gap.

The director, in plain Python

def plan_round(run: Run, story: Story, show: ShowConfig, played_s: float = 0.0,
               transcript: Optional[str] = None) -> RoundPlan:
    n = len(run.rounds) + 1
    rng = random.Random(f"{run.seed}:{n}")
    if not run.rounds:
        return _orientation(run, story, show, rng, sign_on=True)
    if run.rounds[-1].kind in LISTENS:
        return _after_listening(run, story, show, (transcript or "").strip(), rng)
    if run.rounds[-1].kind == "last-exchange":
        return _breakdown(run, story, show, rng)
    if _time_to_listen(run, show, played_s, rng):
        return _repair(run, story, show, rng)
    ended = _aftermath(run)
    if ended:
        return _free(run, story, show, rng, slot="aftermath", words=ended[1], recollects=ended[0])
    if _orientation_due(run, show):
        return _orientation(run, story, show, rng, sign_on=False)
    recalled = _recollection_due(run, show, rng)
    if recalled:
        return _free(run, story, show, rng, slot="recollection", words=recalled[1], recollects=recalled[0])
    return _free(run, story, show, rng)

app/show/director.py — the whole decision ladder of the show

No agent framework: a ladder of ifs. The highlighted line is why the same seed replays the same show — every round draws from a random generator seeded with the run’s seed and the round’s number.

WHY A DIRECTOR IN CODE (decision record ADR-0003, 2026-09-21; accepted 2026-09-23 after a gate experiment) — TalkWithMe made one LLM request per persona, each with its own system prompt, and rewrote the others’ lines as “[Name]: text” user messages. Field-observed problems: labels leaking into speech, a two-role chat template wearing a four-actor play, random followers, nobody owning the story. The new engine: ONE shared context in screenplay form — the cast sheet as the system message, then alternating turns: the director’s instruction (user) and the script lines (assistant) — and ONE streamed request per round for the whole exchange. A director in code owns the story; the model only writes lines. Bonus: llama.cpp’s prompt cache reuses only an identical prefix, which per-persona prompts defeated and one shared context keeps.

WHERE THE DESIGN CAME FROM — the owner’s 2024 prototype: the radio “breaks” to cover the listening window; the cast broadcast among themselves; when it is fixed, they call out and the mic opens about 10 s; a caller makes them pivot to hope, ask for a name, a location, help to escape, supplies; after some exchanges the radio breaks again. Decoded on 2026-09-26 into two modes, Broadcast and Contact.

THE ROUND KINDS (app/show/director.py, about 800 lines) - Broadcast, the receiver off: the sign-on (round 1); orientation repeats every 20 ± 5 free rounds, for listeners just tuning in; free rounds — 2-3 speakers (whoever has been silent longest first), 1-4 lines weighted toward 2-3, holding an event every 2 ± 1 free rounds, the aftermath of a contact, or a recollection of an earlier caller every 15 ± 5; the call (“repair”) between 60 and 180 s of played audio after the receiver went off. - Contact, the receiver on: an exchange when the listener spoke (the addressed character answers first, 2-3 lines, quoting what the voice said, adding one agenda item, ending on a question); a re-call after a silence; the last exchange at the 5 ± 1th answer; then the breakdown; two silences in a row and the receiver is switched off. - The page listens after three kinds: the repair (the call), an exchange, a re-call. (“invitation” in the code is a kind from records made before the modes, kept so old runs still load.)

WHAT IT DRAWS FROM — the story’s data, not code: lab-outbreak has 289 events, 9 agenda items (the first — who are you — opens every contact; the rest at random, never twice in a contact), about 500 tone words, and three overtones with their moods: positive (happy, hopeful, excited, relieved), neutral (calm, doubtful, urgent, curious, determined), negative (sad, afraid, terrified, angry, exhausted). A free round holds its overtone for 4 ± 1 rounds, then drifts to a neighbour; a tone word holds 3 ± 1 rounds.

THE SEED — random.Random(f”{run.seed}:{n}“): one generator per round, seeded with the run’s seed and the round’s number, so a round’s choices do not depend on how many random draws earlier rounds made. With show.seed set, the same seed gives the same show, word for word, on the same box and build (proven 2026-09-22).

A grammar keeps the model in format

The grammar the app sent to llama.cpp for one round:

root    ::= line{1,3}
line    ::= speaker " (" emotion "): " text "\n"
speaker ::= "Daniel" | "Moira" | "Ralph"
emotion ::= "sad" | "afraid" | "terrified" | "angry" | "exhausted"
text    ::= [^\n\[\]()]+

What the model wrote under it:

Daniel (exhausted): We’ve lost power to the security cameras. Over.

Moira (afraid): The samples—they’re spreading. Faster than the math says. Over.

Ralph (angry): This isn’t natural. Someone *made* this. Over.

Round 3 of a run on 2026-10-02: only the round’s speakers, only the moods allowed, at most three lines

GBNF, llama.cpp’s grammar format: the model cannot write anything else. A name outside the round, a missing mood, a fourth line — impossible, not just discouraged. Real request and real output, from the run’s debug files.

GBNF = GGML BNF: Backus-Naur Form in the dialect of GGML, the tensor library under llama.cpp. Sent in the request’s top-level “grammar” field; llama.cpp applies it in the sampler on every token, streamed or not.

READING THE GRAMMAR ON THE SLIDE - root ::= line{1,3} — one to three lines: the round’s line budget, a hard bound, not a request. - speaker — only the round’s speakers; a round may also pin one speaker to the first (or last) line. - emotion — only the moods of the round’s overtone (here the negative five). - text ::= [^[]()]+ — anything but a line break, a bracket or a parenthesis: no stage directions, no extra lines. The app builds a fresh grammar for every round (app/show/grammar.py, 62 lines).

WHY A SCREENPLAY GRAMMAR, NOT JSON (ADR-0003) — the owner’s reason: a JSON format confines the model to the distribution of JSON it saw in training. The quality cost of constrained decoding comes from the model conditioning on a JSON-looking prefix, not from the mask itself; “Name (mood): words” keeps it inside plain text it knows.

WHAT IT COSTS — MEASURED (experiments of 2026-09-22, the A6000) - When the grammar agrees with the model: 0.3 % per token (plain “Name: text”, the ADR-0003 gate), and 0.5 % with the emotion field once the prompt teaches it — and the same text, word for word, with or without the grammar. - When it must overrule the model: 10.4 % per token (11.27 → 12.44 ms), forcing emotion tags a prompt never asked for. In the first round the model even turned its lines into quoted dialogue, conditioning on its own forced tokens; from round 2, with plain lines to copy, the quotes disappeared. - Taught by the prompt, with no grammar at all, 40 of 40 lines carried a legal tag: the grammar is insurance. - Variety: 8 of the 9 emotions used in every arm, no collapse onto one; taught, the model never once picked “happy” in a zombie outbreak.

THE RULE THAT CAME OUT OF IT — every constraint the grammar enforces is also said in the instruction, in the same words each time (“Moira speaks first, then Daniel or Ralph”, “the next three lines”, “each with the emotion in its voice, one of: …”). A grammar that contradicts its prompt changes the model’s style and costs more; one that agrees changes no word. Asked for up to four lines, the model writes four.

READ THE CHAT TEMPLATE FIRST — the grammar constrains only what the model generates, which starts where the template leaves off. Nemotron’s template ends with an empty, closed after /no_think, and with an open without it: a grammar starting with “Name” would then force the script into the model’s private reasoning.

The 32k context, and the trim

A 270-round show, 2026-10-01: rounds cut from the middle (the first 2 and last 4 kept), and the show goes on

Budget 34,000 tokens; the trim fires at 90 % (30,600) and cuts down to 50 % (17,000). It landed at 16,608 and 16,722. A flaw found that day: the trim used to over-cut, more with every trim; fixed and measured — now it lands within one round of its target.

THE PROBLEM — the show is one growing script: every round the model reads all of it (the cast sheet, every kept round’s instruction and reply, the new instruction). It must fit llama.cpp’s context: 16,384 tokens until 2026-10-01, 32,768 since. The trim keeps it inside by removing whole rounds from the middle.

HOW THE APP COUNTS — it does not count tokens itself: it keeps the model server’s own count from each round’s last streamed chunk — prompt_n (read fresh), cache_n (reused from the cache), predicted_n (written). Their sum is the script’s size. Example, round 113 of a drive: 203 fresh + 27,653 cached + 50 written = 27,906. Each round records its share (what it added); the largest seen in 1,824 rounds: 741 tokens (an exchange).

THE TRIM, STEP BY STEP — before each round that asks the model: below 30,600, nothing. At or above it, the rounds still read become candidates except the first 2 and the last 4; the middle one is cut, then outwards, each taking its share off, until the estimate reaches 17,000. Cut rounds stay in the record; the model just stops reading them. The next round’s server count is the truth, so an error never adds up.

THE PAUSE AFTER A TRIM — llama.cpp’s cache holds only an unbroken start of the prompt; cutting the middle means the rest is read fresh: about 8.4 s at 32k (13,922 tokens re-read), once every 100 rounds or more. At 16k with a 14,000 budget: every 22-36 rounds, about 5 s each. With 32k: trims 3-4 times rarer, about 60 % longer, and the model keeps about 2.2 times as much of the show.

WHY 34,000 IF THE CONTEXT IS 32,768 — the trim fires at 90 % of the budget, so the budget may exceed the context as long as 90 % of it plus room for the next instruction (1,000) and the reply (512) fits: 30,600 + 1,000 + 512 = 32,112 ≤ 32,768. When a run opens, the app asks llama.cpp its real context (GET /props) and refuses the run with the arithmetic if it does not fit (tested with a budget of 40,000: refused). The owner (2026-09-28): “I want to keep as much context as possible”.

THE MEMORY — llama.cpp reserves the context when it starts: going from 16k to 32k cost 206 MiB at once, then 76 MiB on first use, then nothing more, flat through a full context and a trim (a hybrid model: only 4 attention layers).

THE FLAW, FOUND AND FIXED (2026-10-01, evening) — the round after the first trim had a negative share (−2,837): the trim had removed more than it estimated. The cause: the call (the Repair) asks the model nothing, so the server reports no size after it, and two rounds per call had no recorded weight — about 600-850 tokens uncounted per call in the cut stretch. The error was not constant (the owner’s doubt was right): it grew with the calls removed, and compounded, because a negative share made the next trim cut more. The owner’s idea: trigger the trim only in the right round. The fix: a round after a Repair counts from the last size the server reported, and the trim fires only before a round that asks the model. Measured with a small budget (8,000) to get many trims: before, the estimate was off by 641 to 4,218 tokens and landed 17-45 % low; after, off by 1 to 3 tokens on every trim, landing within one round of its target. The owner: “it makes the show forget more lines that we intended” — now it forgets what it intends, and no more.

From zero in 7 minutes (ok=33 changed=16); the re-run reports changed=0 in 30 seconds. Before touching anything, the playbook checks it is aimed at the right environment and that no placeholder is left. The price: $0.50-0.59 an hour, from our provider survey of 2026-09-13 — check today’s price before the talk.

WHY IT MATTERS — the owner’s framing (2026-09-17): “deployment is 50% of the MVP”. The deployment machinery was the arc’s deliverable #1, built and proven live on 2026-09-18, before the show engine existed.

THE SHAPE — one playbook (site.yml), four roles, about 475 lines of YAML. It starts at “an SSH-able Ubuntu box exists”: creating the VM stays in the provider’s console, so nothing is provider-specific. Inventories per environment (cloud, local); addresses live in the repo only as a REPLACE_ME placeholder. Roles gate themselves: each applies only on hosts in its own inventory group. Privilege: root declared once, at the play level; any task that runs as another user says so explicitly.

HOW EACH SERVICE IS SUPERVISED — llama.cpp and Whisper: detached Docker containers with restart unless-stopped, so Docker brings them back; tts-serve: a systemd unit, enabled. All three survive SSH disconnects, crashes and reboots without an operator (after a reboot: back in under a minute). No tmux anywhere — the owner: a hard no.

PINNED, ON PURPOSE — llama.cpp image build b11096; whisper-fastapi pinned by digest; tts-serve tag 1.2; the CUDA generation (cu128) and torch 2.9.1 as project variables. The base role asserts the driver can run that CUDA generation — added after a live crash loop on 2026-09-18: a CUDA 13 build on an R570 driver (“driver too old”).

REJECTED, AND WHY — docker-compose: a good pattern, but overkill for two containers with short, proven docker run commands, no traffic between them, one operator and a 3-day timebox (flip trigger: services with dependencies). Terraform / VM provisioning: out of scope for v1.

WHAT A FRESH BOX TAUGHT US (2026-09-22) — a new Ubuntu VM spends its first hour in its own updater (259 packages, 43 minutes); our deploy hit apt’s lock and failed. The fix: a configurable wait for the lock (300 s), announced in the task’s name, and a plain explanation if it times out. Hence “7 minutes once apt has finished”.

THE COST — an RTX A6000, 48 GB, at $0.50-0.59 an hour, Hyperstack (the cheapest suitable GPU in the survey, twice the memory floor). A stopped VM keeps billing; only hibernation stops the meter, with a stock lottery on restore.

Ideas and PRs welcome, and improvements are planned to go back upstream to TalkWithMe

The judge in the loop: a fast small model (about 3B) scores the director’s yes/no questions, and code steers the next instruction; an experiment first. Speaker identification (challenge C3 of the product-definition brainstorm, 2026-09-13, a wishlist item since 2024): a model like ECAPA-TDNN turns a short sample of speech into a speaker embedding, matched against stored ones by cosine similarity, like face recognition.
